\subsection{Purpose}\label{sec:purpose}

The purpose of this document is to two-fold:

\hspace{24pt} Outline the categorical requirements (Section \ref{sec:requirements}) of an intra-networking design specification for hot-swap bus-switched ``modules'' of plug-and-play I${}^2$C devices.

\hspace{24pt} The mission of I${}^2$CIP is to enable rapid prototyping and deployment of plug-and-play embedded systems. The vision of I${}^2$CIP is to establish a scalable framework for the implementation of robust control and communication systems using embedded intra-networking.

\subsection{Scope and Justification}\label{sec:scope}

\subsubsection{I${}^2$C Specification}

\hspace{24pt} From the I${}^2$C Specification Version 7 (2021, \textit{NXP Semiconductors}): 8-bit-oriented one-ended (controller-driven) bidirectional (read \& write) serial communication over a 2-wire bus (data "SDA" \& clock "SCL") for integrated circuit devices ("targets"), including (but not limited to):

\begin{itemize}
    \item \textbf{Remote Multi-Channel Ports}: GPIO banks, internal-clock PWM drivers, A/D and D/A converters, etc.
    \item \textbf{System Devices}: real-time clocks, LCD screens, multiplexers, etc.
    \item \textbf{Data Storage Devices}: EEPROM, SRAM, FRAM, etc.
    \item \textbf{Digital Sensors}: temperature, light, speed, pressure, etc.
\end{itemize}

\hspace{24pt} The I${}^2$C Specification can be imagined as an incomplete analogue to the Internet's OSI Model, with the following layers defined:

\begin{enumerate}[label=SC\arabic*., ref=SC\arabic*]
    \item\label{sc:1} \textbf{Physical Layer}: Compare to RJ45
    \begin{enumerate}[ref=SC1\alph*]
        \item\label{sc:1a} \textbf{VDD \& GND}: +5 VDC
        \item\label{sc:1b} \textbf{SDA \& SCL}: Pull-Up Bias Resistors (10 k$\Omega$)
    \end{enumerate}
    \item\label{sc:2} \textbf{Data Link Layer}: Compare to Ethernet
    \begin{enumerate}[ref=SC2\alph*]
        \item\label{sc:2a} \textbf{Controller}: Bus Speed Control, Start \& Stop Conditions, Multi-Controller Arbitration
        \item\label{sc:2b} \textbf{Targets}: 7-bit Device Addressing, Acknowledgement ("ACK")
        \item\label{sc:2c} \textbf{Packet Structure}: Read \& Write Flags, 8-/16-bit Register Addressing, Byte-Stream Data
    \end{enumerate}
\end{enumerate}

\hspace{24pt} The \textbf{Network} (data routing), \textbf{Transport} (data delivery), and \textbf{Session} (transmission context) layers of the OSI model analogy are not defined by the I${}^2$C Specification. The following proposed extensions to the I${}^2$C Specification, the focus of the \textbf{I${}^2$CIP} design, are intended to fill this gap, enabling \textbf{Presentation} and \textbf{Application} layer functionality to be rapidly implemented by developers for embedded systems.

\subsubsection{Switched-Bus Intra-Networking}

\hspace{24pt} Suppose an I${}^2$C target device $D$ with $N$ possible unique addresses. An I${}^2$C bus controller can communicate with $N$ uniquely-addressed instantiations of $D$ on one bus without conflict or modification to connections.

\hspace{24pt} Suppose an I${}^2$C target device with $M$ possible unique addresses that acts as a multiplexer and repeater ("switch") for $B$ bitwise-enabled output busses ("subnetworks"). An I${}^2$C bus controller can communicate with $M * B * N$ independently-addressable instantiations of $D$ across $M * B$ subnetworks by setting ONE active output bus on each of the $M$ switches (and disabling ALL on the remaining $M - 1$).

\hspace{24pt} Example: For $M = 8$ switches with $B = 8$ subnetworks each, the total number of uniquely-addressable instantiations of $D$ on an I${}^2$CIP intra-network is $8 * 8 * N = 64N$, effectively enabling a 64-fold increase in independently-addressable targets of all types by a single controller.

\subsubsection{State Flow and Debugging}

\hspace{24pt} Basic state management for control flow specification is implemented by FiniteStateMachine (\texttt{FSM}) constructs. The \texttt{State<T>} template class allows for the definition of stateful primitive interfaces, to which conditional callbacks can be attached; for example, an always-executed callback that controls PWM output when a \texttt{Variable} (\texttt{State<Number>}) is not equal to \texttt{NAN}, or a ``latching'' callback that controls a GPIO output only when a \texttt{Flag} (\texttt{State<bool>}) changes from true to false or false to true. Debugging state flow and I$^2$C bus interactions is facilitated through DebugJson, which provides bidirectional newline-delimited JSON communication for monitoring and controlling I$^2$C bus interactions (``command'') and system state transitions (``configuration'', ``event'', and ``interval'').

\subsection{Definitions}\label{sec:definitions}

A number of useful definitions have emerged from the above scoping:
\begin{enumerate}
    \item \textbf{Transaction}: A single I$^2$C communication operation between a controller and a target, consisting of a start condition, an address phase, a data phase, and a stop condition.
    \item \textbf{Switch}: An I${}^2$C target that acts as a repeater for bitwise multiplexed output busses.
    \item \textbf{Subnetwork}: A specific output bus of a specified switch.
    \item \textbf{Intra-Network}: A term referring to ALL routable targets (not including switches) on ALL subnets across ALL of a controller's I${}^2$C busses (in the case of multiple controller busses).
    \item \textbf{Fully-Qualified Address (FQA)}: A unique intra-network routing location identifier, encoding: a specific I${}^2$C bus (in the case of multiple controller busses), and; a specific subnetwork, and; a target's address.
    \item \textbf{Device Identification}: A unique ASCII string identifier for a class of I${}^2$C target devices, derived from hardware specification.
    \item \textbf{Module}: A switch, and a physical collection of targets located on the switch's subnetworks, and a writable data storage target with a predetermined FQA containing all FQAs and device IDs for all targets on this switch's subnetworks.
\end{enumerate}

\section{Framing}\label{sec:framing}

\subsection{Problem Statement}\label{sec:opportunity}

\hspace{24pt} Design, implement, and test an intranetwork framework of I$^2$C targets and modules that ensures unique fully-qualified addressing, unique device identification, and robust communication across all switches, subnetworks, and targets.

\subsection{Solution Requirements}\label{sec:requirements}

\begin{enumerate}[label=R\arabic*., ref=R\arabic*]
    \item\label{r:1} \textbf{Must} achieve Quality-of-Service (QoS) level 2 for all I$^2$C transactions on the intranetwork.
    \item\label{r:2} \textbf{Must} achieve unique fully-qualified addressing for all I$^2$C targets on the intranetwork.
    \item\label{r:3} \textbf{Must} achieve unique device identification for all I$^2$C targets on the intranetwork.
    \item\label{r:4} \textbf{Must} achieve switch multiplexing for all subnetworks on the intranetwork.
    \item\label{r:5} \textbf{Must} achieve individual subnetwork addressing for all I$^2$C targets on the intranetwork.
    \item\label{r:6} \textbf{Must} achieve individual target control for all I$^2$C targets on the intranetwork, subnetworked and non-subnetworked.
    \item\label{r:7} \textbf{Must} achieve error detection and handling for all I$^2$C transactions on the intranetwork.
